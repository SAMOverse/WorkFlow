### LL-001: `npm install` Fails Reliably Inside This Project's Google-Drive-Synced Folder
`[Environment / Google Drive]`
Confirmed twice, reproducibly, right at scaffolding time: `npm install` run directly inside `H:\My Drive\Claude Projects\WorkFlow\` fails with `EPERM: operation not permitted, rmdir ...` during npm's own cleanup pass, followed by `EBADF: bad file descriptor`, leaving a near-empty `node_modules` (no `.bin`, nothing usable). The exact same `package.json` installed cleanly (87 packages, clean build) copied to a plain local temp folder outside Drive sync. This is the same class of issue the sibling SAL Operations project has documented and partially worked around (Drive's virtual filesystem adds real per-file I/O overhead and, for npm specifically, breaks its rename/rmdir dance during a large multi-file install like `node_modules`) — but here it's an outright failure, not just slowness.
**Why:** Google Drive's local sync client intercepts file operations on a virtual filesystem layer; npm's install process does rapid create/rename/delete cycles across thousands of small files (`node_modules`), which Drive's sync layer doesn't handle as a plain local disk would.
**How to apply:** Never run `npm install` (or anything that writes a large `node_modules`) directly inside this repo's Drive-synced path. `node_modules` is gitignored anyway, so nothing is lost by keeping it out of Drive entirely — either work from a plain local git clone (recommended; matches what SAL Operations' own unresolved "Someday" item already recommends doing for itself), or, if working directly in the Drive folder is preferred for some other reason, install into a local path and symlink `node_modules` back in. `git` operations (status/add/commit/push) on the source files themselves are unaffected — only npm's own install-time file churn triggers this.

### LL-002: A Loose `^` Version Range on `eslint-plugin-react-hooks` Resolved to an Incompatible Config Shape
`[Tooling / ESLint]`
Scaffolded `eslint.config.js` by copying the sibling SAL Operations dashboard's working pattern (`reactHooks.configs.flat.recommended`), but wrote `"eslint-plugin-react-hooks": "^5.0.0"` in `package.json` from memory instead of checking what version the sibling project actually has installed (`^7.1.1`). npm resolved `^5.0.0` to `5.2.0` — a real published version, but one whose `configs` export dropped the `flat` namespace entirely (it exposes `recommended`, `recommended-legacy`, `recommended-latest` instead), so the copied config line crashed with `Cannot read properties of undefined (reading 'recommended')`. Fixed by pinning the same major version range the sibling project actually uses (`^7.1.1`), not by chasing the newer API shape — confirmed the original `flat.recommended` line is correct once the version matches.
**Why:** A config snippet copied from a working sibling project is only actually valid for the *version* of that dependency the sibling project has installed — the same import path (`configs.flat.recommended`) is a real, working API in one major version and a `TypeError` in another. Guessing a version range "from memory" instead of checking the sibling's `package.json` directly is exactly how this mismatch happened.
**How to apply:** When copying a config pattern (ESLint, Babel, bundler config, etc.) from another project in this same account, copy its dependency *versions* too, not just the config file's contents — grep the sibling project's `package.json` for the exact range in use rather than writing a plausible-looking one from memory. If a copied config throws on a method/property that "should" exist, suspect a version mismatch before assuming the copied code is wrong.

### LL-003: A Sibling Project's "Critical Rule" Was Carried Into CLAUDE.md Without Re-Confirming It Against This Project's Own Requirements
`[Process / Requirements]`
CLAUDE.md's original "Critical Rules" section stated "click-to-edit, not drag-to-resize" as a rule to apply "from day one," inherited wholesale from SAL Operations' own CLAUDE.md. It got applied to the first interactive mockup (no drag interaction at all) before the user had ever actually weighed in on it for WorkFlow specifically. When the user later asked for drag-to-resize and drag-to-link-dependencies, they said explicitly they hadn't ruled drag out and didn't know where that restriction came from — because they hadn't stated it; it arrived through carried-forward scaffolding, not through a decision made for this project.
**Why:** A rule inherited from a sibling project's real, hard-won lesson is still just an assumption until it's confirmed against *this* project's actual requirements — even when it's labeled "critical" and even when the underlying engineering rationale (ambiguous intent on a drag, silent-wrong-edit risk) is sound in the abstract.
**How to apply:** When a "carried forward" rule from another project in this account is about to shape a concrete deliverable (not just inform it), surface it to the user explicitly before building against it, rather than silently treating it as settled. If the user overrides it, update CLAUDE.md in the same session rather than leaving the doc and the actual product decision out of sync.

### LL-004: A Correct Fix Can Still Be the Wrong Diagnosis — Chase the Root Cause, Not the First Plausible Bug
`[Frontend / CSS / Debugging]`
The interactive mockup's Gantt/Network/Guide panes reportedly could not scroll, in either direction. First diagnosis: the scroll containers (`.board-scroll`, `.net-scroll`, `.guide-scroll`) were missing `min-height:0`, a real, well-known flexbox trap (a `flex:1` item's default minimum height is "as tall as its content," so it grows to fit everything instead of clipping and scrolling). That fix was applied, published, and **did not resolve the bug** — the user reported it was still broken, plus a new, unrelated symptom (a dead vertical scrollbar sitting on the tab bar, caused by a *different* earlier fix: `overflow-x:auto` implicitly sets `overflow-y:auto` too per the CSS spec when only one axis is declared). Re-diagnosing from scratch rather than assuming the first fix "mostly" worked led to the actual root cause: `body{height:100%}` was set, but `html{height:100%}` was not — and this project's own loaded `artifact-design` skill guidance *explicitly* says a one-screen app needs `height:100%` on **both** `html` and `body`, specifically instead of `100vh`, so that the platform's safe-area padding on `:root` is respected. Without a definite height on `html`, `body{height:100%}` resolves to `auto`, and the entire flex chain below it — including the correct `min-height:0` fixes — has nothing to actually shrink against. The `min-height:0` fix was real and necessary, but not sufficient, and reported as fixed before it was verified against the actual complaint.
**Why:** A plausible, textbook-correct CSS fix (min-height:0 is a genuinely common flexbox bug) can coexist with a deeper, unrelated root cause. Publishing a fix and reporting "fixed" without being able to visually verify it in a real browser meant the failure only surfaced through another round of user feedback — twice. The second, correct diagnosis was sitting in already-loaded skill instructions from earlier in the very same session, not something that needed rediscovering.
**How to apply:** When a fix doesn't resolve a reported bug on retry, don't reach for the next plausible CSS hypothesis in isolation — re-check it against any platform/skill guidance already loaded in the session first (it may directly specify the exact setup required, as `artifact-design` did here for `html`+`body` height). When a fix can't be visually verified before reporting it back, say so plainly rather than implying confidence the tooling can't back up.

### LL-005: `FileReader.readAsBinaryString` Is Non-Standard — Use `readAsArrayBuffer` for SheetJS/XLSX Parsing
`[Frontend / Import / Browser APIs]`
The Excel/CSV importer (built on the SheetJS `xlsx` library) read the uploaded file with `reader.readAsBinaryString(file)` and `XLSX.read(reader.result, {type:'binary'})` — a pattern copied from older SheetJS examples. The user reported the Excel import simply wasn't recognized. `readAsBinaryString` was never part of the FileReader spec (it was a legacy Firefox/Mozilla extension method); modern browser support for it is inconsistent, unlike the standard `readAsArrayBuffer`. Switched to `reader.readAsArrayBuffer(file)` with `XLSX.read(new Uint8Array(reader.result), {type:'array'})`, the pattern SheetJS's own current docs recommend.
**Why:** Copying a working-looking code snippet (including from an authoritative library's own older examples) doesn't guarantee the API it calls is still broadly supported — non-standard/legacy browser methods are an easy thing to carry forward unnoticed.
**How to apply:** For file-reading code via `FileReader`, prefer `readAsArrayBuffer` (standard, universally supported) over `readAsBinaryString`/`readAsDataURL` unless a library specifically requires one of those. When wiring up a third-party parsing library, check its *current* docs for the recommended input type, not just whichever snippet is easiest to find.
